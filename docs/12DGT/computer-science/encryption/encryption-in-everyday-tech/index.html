Computer Science · Encryption Unit · Session 5 of 8

You used at least three of these before lunch.

By now you've met symmetric encryption, public-key encryption, and hashing individually. This session is about recognising them out in the wild — in the card you tap, the health record a hospital sends, and the growing list of everyday devices that quietly depend on all three.

Session time: 60 minutes·Homework: none this session

Executive summary

Goal: identify which type of encryption (or hashing) is at work in a range of real, everyday technologies, and explain the opportunity each one provides.

Before you start​

Before you start

Look back at your list from Session 1 ("three apps or systems you trust"). Add to it: how many different pieces of technology have you used today that almost certainly relied on encryption or hashing? Aim for at least five, and be specific (not just "my phone" — what on your phone?).

Contactless payments​

Tapping a card or phone on an EFTPOS terminal uses a chip-based standard (EMV) that generates a unique, single-use transaction code for every single tap — even if you tap the same card on the same terminal twice in a row, the code sent is different each time. This is deliberately similar to the rolling-code garage door remote from Session 2: a fixed, reusable card number sent in the clear would be trivial to intercept and replay, so the system is built to make every transaction cryptographically unique.

When you add a card to Apple Pay or Google Pay, the system goes a step further using tokenisation: your actual card number is never stored on the phone or sent to the terminal at all. Instead, a substitute number (a token) tied to that specific phone is used, and it's meaningless if intercepted or stolen, because it can't be used anywhere else.

Case file: a hospital referral

When a GP refers a patient to a specialist at a different hospital, the patient's file — history, medication, test results — has to move between two separate healthcare organisations' computer systems. Health information is amongst the most sensitive personal data that exists, and in most countries (including New Zealand, under the Health Information Privacy Code) it's subject to strict legal protection.

Encryption here typically combines several ideas from this unit: the connection between the two health systems is usually secured much like HTTPS (Session 3), using public-key encryption to establish trust and a temporary shared key; the file itself may additionally be encrypted at rest (Session 2, symmetric encryption with AES) while stored on either hospital's servers; and staff logins to access the record depend on properly hashed and salted passwords (Session 4).

The opportunity this creates: without strong encryption, health systems could not digitise patient records or share them between specialists at all — the legal and ethical risk would be too high. Encryption is what makes it possible to get faster, better-coordinated care from multiple providers, not just what makes it safe.

Activity: match the technology​

For each technology below, name which concept from this unit (symmetric encryption, public-key encryption/HTTPS, or hashing/salting) is most directly responsible for protecting it, and explain your reasoning in one sentence.

  1. A hospital's stored database of patient records, sitting on its own servers.
  2. A doctor logging into that hospital's system with a username and password.
  3. A patient's referral letter being transmitted, in real time, to a specialist at another hospital.
  4. A contactless card generating a different transaction code every time it's tapped.
Reveal model answers and check your work
  1. Symmetric encryption (AES). Large amounts of stored data are typically encrypted at rest using a fast symmetric algorithm, since there's no need to solve a key-exchange problem for data that isn't being transmitted to someone else.
  2. Hashing and salting. The login system compares a hash of the entered password against the stored, salted hash — it should never store or compare the actual password.
  3. Public-key encryption / HTTPS-style connection. Two systems that have never directly shared a key before need to establish trust and agree on a secure channel — the same key-exchange problem HTTPS solves for websites.
  4. Symmetric encryption, generating a unique code per transaction — conceptually similar to a rolling-code system, so a captured code can't simply be replayed.

Common mistake

A common mistake in exam answers is naming a technology (like "encryption" or "HTTPS") without explaining which specific problem it solves in that scenario. "It uses encryption to keep data safe" is too vague — always say safe from what, and how.

Exit question​

Choose one real, everyday technology not already discussed in this session, and explain which type of encryption (or hashing) it most likely relies on, and why.
